This page covers a production deployment of all three servers from source. It assumes you have already run the [Quick start](#/getting-started/quick-start) once and know how the servers connect. To run the same setup in containers, see [Docker](#/getting-started/docker).

## What changes from development

| Area | Development | Production |
| --- | --- | --- |
| Environment file | `.env.development` | `.env.production` in each repository |
| Start command | `bun development` | `bun production` |
| TLS | Off for HTTP, local self signed certificate for WebTransport | On everywhere, with a certificate for your domain |
| Secrets | Throwaway values | Long random values, different from development |
| Database | Local MySQL | A MySQL server with its own user and a strong password |

:::danger Keep production secrets out of version control
`.env.production` is ignored by git in all three repositories. Keep it that way, and never copy keys from a development file into production.
:::

## Order of work

1. Create the database and its user.
2. Get a TLS certificate and place it in each repository.
3. Write the three `.env.production` files.
4. Asset server: start it.
5. Gateway: run its setup, start it.
6. Engine: run its setup, run the gateway setup once more, start it.

## 1. Database

The gateway and the engine use one database. Create it and a user that owns it:

```sql title="MySQL"
CREATE DATABASE frostfire_forge;
CREATE USER 'frostfire'@'localhost' IDENTIFIED BY 'change-me';
GRANT ALL PRIVILEGES ON frostfire_forge.* TO 'frostfire'@'localhost';
FLUSH PRIVILEGES;
```

Use the same `DATABASE_NAME`, `DATABASE_USER` and `DATABASE_PASSWORD` in the gateway and the engine. See [Database](#/engine/database) for pool sizes and SSL options.

## 2. TLS certificates

Each server reads its certificate from three variables:

```env title="TLS block, the same in all three repositories"
HTTP_USE_SSL=true
TLS_CERT_PATH=./src/certs/cert.pem
TLS_KEY_PATH=./src/certs/key.pem
TLS_CA_PATH=./src/certs/cert.ca-bundle
```

```text title="Expected files in each repository"
src/certs/
  cert.pem          server certificate
  key.pem           private key
  cert.ca-bundle    CA chain (optional)
```

What each server does with them:

| Server | Behaviour |
| --- | --- |
| Gateway | The reverse proxy (web) and the gateway server share the one certificate. With TLS on, the web listener moves to `WEBSRV_PORTSSL` (443) and the gateway server to `GATEWAY_PORTSSL` (9443). The plain ports answer with a redirect to HTTPS. |
| Asset server | Serves HTTPS on `WEBSRV_PORTSSL` and redirects from `WEBSRV_PORT`. |
| Engine | The same certificate is used for the HTTP API and for WebTransport. WebTransport **always** needs a certificate, with or without `HTTP_USE_SSL`. |

:::warning If the files are missing, TLS is silently off
When `HTTP_USE_SSL=true` but the certificate or key cannot be found, the gateway and the asset server log `SSL requested but certificates not found` and serve plain HTTP on the plain port instead. Check the startup log.
:::

### The engine's WebTransport certificate

- In production, use a certificate from a public certificate authority that covers the name in `PUBLIC_HOST`. Browsers then validate it the normal way, and the engine's `/wt-cert-hash` endpoint answers 404 because the certificate is not one meant for pinning.
- The engine checks the certificate at startup. It refuses to start with an expired or unreadable certificate, warns when fewer than 3 days remain, and warns when the certificate does not cover `PUBLIC_HOST` or `SERVER_HOST`.
- A CA signed certificate is never regenerated by the engine. Renew it yourself and restart.

More detail is in [TLS](#/gateway/tls) and [Networking](#/engine/networking).

## 3. Environment files

Start each file from the repository's `.env.example`. The blocks below show the values that tie the servers together, with placeholders. Replace `play.example.com` and every `change-me` value with your own.

### Asset server

```env title="Frostfire-Forge-Assets/.env.production"
ASSETS_PATH=./src/assets

WEBSRV_PORT=8081
WEBSRV_PORTSSL=8082
WEBSRV_INTERNAL_PORT=8083
HTTP_USE_SSL=true

TLS_CERT_PATH=./src/certs/cert.pem
TLS_KEY_PATH=./src/certs/key.pem
TLS_CA_PATH=./src/certs/cert.ca-bundle

ASSET_SERVER_AUTH_KEY=change-me-asset-key
```

The full list is in [asset server configuration](#/assets/configuration). Keep the game's own assets outside the repository if you can, see [Asset paths](#/assets/asset-paths).

### Gateway

```env title="Frostfire-Forge-Gateway/.env.production"
DATABASE_ENGINE=mysql
DATABASE_HOST=localhost
DATABASE_PORT=3306
DATABASE_NAME=frostfire_forge
DATABASE_USER=frostfire
DATABASE_PASSWORD=change-me
SQL_SSL_MODE=DISABLED

WEBSRV_PORT=80
WEBSRV_PORTSSL=443
WEBSRV_INTERNAL_PORT=8080
HTTP_USE_SSL=true

TLS_CERT_PATH=./src/certs/cert.pem
TLS_KEY_PATH=./src/certs/key.pem
TLS_CA_PATH=./src/certs/cert.ca-bundle

GATEWAY_PORT=9999
GATEWAY_PORTSSL=9443
GATEWAY_INTERNAL_PORT=9998
GATEWAY_AUTH_KEY=change-me-gateway-key
GATEWAY_GAME_SERVER_SECRET=change-me-shared-secret

DOMAIN=https://play.example.com
GAME_NAME=My Game
LOG_LEVEL=info

ASSET_SERVER_URL=https://play.example.com:8082
GUEST_MODE_ENABLED=false
```

Email, guest mode, timeouts and the rest are in [gateway configuration](#/gateway/configuration).

### Engine

The first time you run `bun create-config --environment production` (the `production` and `setup-production` scripts do it for you), an empty `.env.production` template is written if the file does not exist. Fill it in before you go on.

```env title="Frostfire-Forge/.env.production"
DATABASE_ENGINE=mysql
DATABASE_HOST=localhost
DATABASE_PORT=3306
DATABASE_NAME=frostfire_forge
DATABASE_USER=frostfire
DATABASE_PASSWORD=change-me
SQL_SSL_MODE=DISABLED

WEBSRV_PORT=3000
WEBSRV_PORTSSL=3000
WEBSRV_INTERNAL_PORT=3002
HTTP_USE_SSL=true
WEBSRV_HTTP3=false

TLS_CERT_PATH=./src/certs/cert.pem
TLS_KEY_PATH=./src/certs/key.pem
TLS_CA_PATH=./src/certs/cert.ca-bundle

GAME_NAME=My Game
LOG_LEVEL=info
CORS_ALLOWED_ORIGINS=https://play.example.com

SERVER_ID=realm-1
SERVER_DESCRIPTION=My Realm
SERVER_HOST=play.example.com
PUBLIC_HOST=play.example.com

GATEWAY_URL=https://play.example.com:9443
GATEWAY_AUTH_KEY=change-me-gateway-key
GATEWAY_GAME_SERVER_SECRET=change-me-shared-secret

ASSET_SERVER_URL=https://play.example.com:8082
ASSET_SERVER_AUTH_KEY=change-me-asset-key

CACHE=memory
```

The full list, including `SESSION_KEY`, `RSA_PASSPHRASE`, worker pool sizes and Redis, is in [engine configuration](#/engine/configuration).

### Addresses for players and addresses for servers

`ASSET_SERVER_URL` and `PUBLIC_HOST` are sent to the player's browser, so they must be reachable from the internet. When the servers sit on the same machine or private network, you can give the engine a second, internal address for its own calls:

```env title="Optional, in the engine's .env.production"
GATEWAY_INTERNAL_URL=https://127.0.0.1:9998
ASSET_SERVER_INTERNAL_URL=https://127.0.0.1:8083
```

The engine uses these for registration, heartbeats, map sync and editor saves, and keeps `ASSET_SERVER_URL` for the browser. The ports are each server's internal port, which only listens on `127.0.0.1`.

:::warning Server to server HTTPS does not verify certificates
Calls between the servers over `https://` are made with certificate verification turned off, which is what lets an address like `https://127.0.0.1:9998` work with a certificate issued for your domain. Keep these links on loopback or a network you trust.
:::

## 4. Start the asset server

```bash title="In Frostfire-Forge-Assets"
bun install
bun production
```

## 5. Set up and start the gateway

```bash title="In Frostfire-Forge-Gateway"
bun install
bun setup
bun production
```

`bun setup` uses `.env.production`. It creates the database if needed, the `allowed_ips` and `blocked_ips` tables, and adds the two-factor columns to `accounts` when that table exists.

## 6. Set up and start the engine

```bash title="In Frostfire-Forge"
bun install
bun setup-production
```

`bun setup-production` generates the config files in `src/config` and then creates every game table, including `accounts`, with `.env.production`.

Now run the gateway setup a second time so the two-factor columns are added to the new `accounts` table. The script is safe to repeat:

```bash title="In Frostfire-Forge-Gateway"
bun setup
```

Then start the engine:

```bash title="In Frostfire-Forge"
bun production
```

`bun production` starts the server with `--sql-preconnect`.

The engine setup creates no accounts. Make the first admin with the gateway's script, then open the link it prints to set the password:

```bash title="In Frostfire-Forge-Gateway"
bun create-admin <username> <email>
```

The link is built from `DOMAIN` and works once. The account is created verified, so the admin can log in before a mail server is configured.

:::warning Databases set up before this change
Earlier versions of the engine setup inserted an account named `demo_user` with a publicly documented password and admin permissions. Setup no longer creates it, but it does not remove one that already exists. Change its password or delete the account.
:::

## Firewall

| Port | Transport | Server | Open to |
| --- | --- | --- | --- |
| 80, 443 | TCP (and UDP 443 for HTTP/3) | Gateway web | Everyone |
| 3000 | UDP and TCP | Engine | Everyone |
| Asset server SSL port | TCP (and UDP for HTTP/3) | Asset server | Everyone |
| 9443 | TCP | Gateway server | Game engines on other hosts, and whoever uses the dashboard |
| 3306 | TCP | MySQL | The gateway and the engines only |

The internal ports (8080, 9998, 3002 and the asset server's internal port) only listen on `127.0.0.1` and need no rule.

## Checks after startup

```bash title="Health checks"
curl https://play.example.com:8082/status
curl https://play.example.com:9443/status
curl https://play.example.com:3000/status
```

- The gateway's `/status` should list your realm with `"status":"online"`.
- The engine log should show the map sync, the registration with the gateway and `WebTransport listening on UDP port 3000`.
- Log in through the site and enter the realm from a Chromium based browser on another network, so that you test the firewall as well.

## Adding realms

Every engine instance is a realm. To add one, run another engine with its own `SERVER_ID`, `SERVER_DESCRIPTION`, `PUBLIC_HOST` and port, and the same `GATEWAY_AUTH_KEY` and `GATEWAY_GAME_SERVER_SECRET`. It appears on the realm selection page as soon as it registers. See [Game servers](#/gateway/game-servers) and [Realm whitelist](#/engine/realm-whitelist).
